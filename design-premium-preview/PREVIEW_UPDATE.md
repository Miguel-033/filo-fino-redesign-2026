# Как позднее безопасно обновить интерактивный preview

**Инструкция; сейчас ничего из неё не опубликовано.** Подготовка ветки и merge в publishing-ветку — разные действия. Merge/обновление `gh-pages-preview` делать только после отдельного решения владельца: если Pages включён, это запускает публикацию.

После отдельного принятия PR №4 при необходимости переназначить base нового PR на main и проверить diff.

## 1. Сначала проверить исходник

1. Получить полный checkout новой ветки и записать **точный принятый SHA**, а не использовать плавающий HEAD.
2. Открыть локально, выполнить `verify-preview.cjs` по README, просмотреть новые desktop/mobile-снимки. Сейчас эти проверки ещё не завершены.
3. Проверить пять контекстов WhatsApp, все восемь фото, галерею/zoom/стрелки/закрытие и четыре этапа. На шаге Afilar должна быть заглушка, а не ролик.
4. Убедиться, что часы, телефон и адрес подтверждены; устранить известное расхождение расписания до будущей публикации.
5. Получить решение владельца о публикации конкретной версии.

## 2. Подготовить отдельную ветку обновления preview

Не работать прямо в `gh-pages-preview`. Сначала `git fetch origin` и сравнить publishing SHA с записанным выше. Если ветка изменилась — изучить изменения и сохранить их, не перезаписывать их старой копией.

Создать, например, `preview/premium-media-review` **от актуальной `origin/gh-pages-preview`**, лучше в отдельном worktree. В этой ветке собрать только статическую копию из принятого SHA:

| Источник | Куда в publishing-копии |
|---|---|
| `design-premium-preview/index.html` | `index.html` |
| `design-premium-preview/premium.css` | `premium.css` |
| `design-premium-preview/refinement.css` | `refinement.css` |
| `design-premium-preview/premium.js` | `premium.js` |
| `design-premium-preview/assets/` | `assets/` |

В копии HTML заменить **каждый** `href="/…"` на `href="https://filofino.es/…"` — услуги и правовые страницы. Якоря `#…`, локальные `assets/…`, WhatsApp, телефон и Maps не менять. Это только адаптация ссылок для подкаталога GitHub Pages, существующие URL сохраняются. Не копировать весь рабочий сайт, `.agents`, исходный репозиторий или каталог скриншотов в publishing-корень.

Сохранить `.nojekyll`, `noindex, nofollow`, локальные лицензии шрифтов и реестр происхождения фотографий. В README publishing-копии записать исходный SHA и дату. **Не добавлять CNAME, домен, DNS, аналитику или workflow.** Custom domain должен остаться пустым.

Локально обслужить копию под префиксом `/filo-fino-redesign-2026/`, проверить ресурсы и ссылки, отсутствие 404 и ошибок JS. Сравнить diff с publishing-веткой: только перечисленные файлы и необходимые assets. Создать отдельный PR в `gh-pages-preview`; push только новой review-ветки сам по себе не должен затрагивать publishing-ветку. Перед push проверить правила Actions/Pages репозитория.

## 3. Публикация владельцем

После одобрения конкретного preview-PR владелец может выполнить обычный merge в `gh-pages-preview`. Без force-push. Если Pages настроен на эту ветку, GitHub начнёт деплой — это именно действие публикации. Сейчас оно не выполнялось.

Не менять Settings → Pages без необходимости. Если публикация ещё не включена, включать её — отдельное решение владельца. Ожидаемый адрес из существующей инструкции: `https://miguel-033.github.io/filo-fino-redesign-2026/`; актуальную ссылку брать из Settings → Pages → Visit site. Наличие активного публичного preview в этой работе не проверялось.

После публикации проверить мобильную/desktop-страницу, ресурсы, все ссылки и интерактивные состояния. При проблемах сделать revert preview-коммита/merge (сохранив новые изменения других авторов), а не переписывать историю. При необходимости остановить доступ — Unpublish site в Pages, затем отключить publishing-ветку, чтобы будущий push не опубликовал её снова.

- Добавлять только реально проверенные исходники владельца; обновлять `assets/media-manifest.json` и `assets/SOURCES.md`.
- `workshop-entrance`: заменить типографическую композицию на настоящее фото входа, прописать корректный alt, размеры и объектное позиционирование. Подпись о pending убрать после замены.
- `stages` в `premium.js`: заменить временные фото шагов 01/02/04 на соответствующие кадры; исходный шаг 01 синхронизировать с HTML. Не объявлять кадр проверкой реза, если её на нём нет.
- `process-video`: использовать существующую рамку `.process-frame` 4:3 и слот `data-media-slot="process-video"`. После отдельного согласования ролика добавить нативный player с controls, poster, `preload="none"` и `playsinline`; без autoplay, аудио и фоновой загрузки. Сохранить доступную текстовую альтернативу и статичный poster. Сейчас player и видеофайлы намеренно отсутствуют.
- Новые фотографии галереи добавлять в `photographs`; первые три индекса связаны с превью. Счётчик обновляется автоматически, но подписи/количество в исходном HTML без JS нужно синхронизировать вручную.
- После любой замены повторить проверки и снять новые скриншоты; публикация снова только отдельным решением.
